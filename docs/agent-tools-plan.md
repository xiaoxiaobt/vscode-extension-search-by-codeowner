# Agent tools for CODEOWNERS context

## Goal

Expose CODEOWNERS-aware workspace context to VS Code AI agents through native Language Model tools:

1. List files assigned to a concrete CODEOWNER.
2. Search the contents of files assigned to a concrete CODEOWNER.
3. Discover matching CODEOWNERS names from a partial owner string, including values without the org prefix.

`Unowned` and `Owned by all` are intentionally outside this agent-tool contract. The existing webview can continue to expose those virtual filters for native Search.

## Tool contract

The file-listing and content-search tools accept a concrete `owner` value present in the loaded CODEOWNERS file. They also accept:

- `excludeGitIgnore`: exclude `.gitignore` patterns; defaults to `true`.
- `useVscodeExcludes`: exclude `files.exclude` and `search.exclude` settings; defaults to `true`.
- `maxResults`: bound the returned file list; defaults to `1000`, with a maximum of `10000`.

The content-search tool additionally accepts:

- `query`: required text or regular expression.
- `caseSensitive`: defaults to `false`.
- `isRegex`: treat the query as a JavaScript regular expression; defaults to `false`.
- `matchWholeWord`: require word boundaries around the match; defaults to `false`.

The matching-owner tool accepts a partial `query` such as `network`, `semconv-network`, or `@open-telemetry/semconv-network-approvers` and returns the canonical CODEOWNERS names that contain it, case-insensitively. It compares against the full owner, the local team/user segment, and the org-less form so users can omit the org prefix.

Results contain URI/path pairs, counts, and truncation or skipped-file metadata. Invalid owners, empty queries, and invalid regular expressions return structured errors.

## Native API boundary

VS Code provides stable `workspace.findFiles`, which is used to enumerate candidate files. Candidate globs are generated by `CodeOwnerService` and rewritten with the existing multi-root workspace support. Each candidate is then classified with `getCodeOwnerForFile` so final CODEOWNERS rule precedence remains authoritative, and overlapping workspace roots are deduplicated.

VS Code does not provide a stable public API that invokes its built-in text-search engine and returns structured results to an extension. The content-search tool therefore reads the ownership-matching candidates with `workspace.fs.readFile` and applies the requested matcher in the extension. Binary-looking files and unreadable files are skipped and counted.

The existing webview continues to use the native Search UI command for interactive searches. That internal command is not used by the agent tools because it opens UI and does not return result data.

## Implementation notes

- Tools are registered with `vscode.lm.registerTool` and declared through `contributes.languageModelTools`.
- Tool registration is independent of the webview lifecycle, so agents can invoke the tools when the view is closed.
- `workspace.findFiles` cancellation is propagated through the Language Model tool cancellation token.
- VS Code default exclusions are disabled when `useVscodeExcludes` is `false`; explicit `files.exclude` and `search.exclude` entries are also added when it is `true`.
- `.gitignore` patterns are added through the existing `GitIgnoreService` when `excludeGitIgnore` is `true`.

## Verification

Compile and lint the extension, then invoke both tools in single-root and multi-root workspaces. Verify concrete-owner selection, last-rule-wins classification, URI deduplication, exclusion toggles, case sensitivity, whole-word matching, regex matching, invalid regex errors, cancellation, and result truncation.
